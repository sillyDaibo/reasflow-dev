# OptiRepro 项目进展与自动复现能力分析

本文面向项目负责人，回答一个核心问题：**现有 Pipeline 已经能把优化论文复现到什么程度，产出的代码距离可供后续研究依赖的算法库还有多远？**

分析依据是 2026-09-06 已核对的 CPU30 第 003 次运行，其中 16 篇论文的 A/B 复现与两层 Judge 都已完成。本文所说的“当前进展”指这批已经有证据可分析的进展；其后服务器是否又完成了任务，尚未在本文更新。两侧分别为 A：Codex 原生配置；B：同一 Codex 基座加载 ReasFlow Experiment Agent 配置。

阅读顺序：先看项目阶段与能力结论，再看 ReasFlow 的实际使用和关键执行过程；逐篇章节给出完整主张、结果与问题，最后提出下一步工作。所有入库用途判断均为基于现有证据的建议，不是已经通过独立验收的认证。

## 1. 项目要建立什么，目前走到了哪一步

项目要持续把优化领域论文转化为可运行、可理解、可复用的算法实现，使后续研究能够检索和参考已有方法，组合合适的算法与实验流程，并开展新的设计与比较。自动复现 Pipeline 是生产这些研究资产的手段。

一篇论文的代码进入这样的库，至少要回答：实现的是哪个数学方法，在哪些问题假设下适用，实验采用什么协议，哪些主张有实际结果支持，以及哪些部分仍存在偏离。否则，下游研究可能选到一个名称正确、更新式却已经改变的“基线”，随后所有比较都失去明确含义。

### 1.1 已经完成的进展

**批量任务已经产生了真实的代码、实验结果和可检查的运行过程。** 已核对的 16 对任务覆盖鲁棒分布式学习、随机重排、联邦优化、变分不等式、流形优化、图像逆问题等不同方法。它们提供了研究 Codex 能力边界的实际样本。

| 项目环节 | 现有证据支持的进展 | 距离项目目标的缺口 |
| --- | --- | --- |
| 任务组织与执行 | 已有论文输入、A/B 工作区、持续执行与外部维护、交付和 Judge 的批量工作链条 | 完成子集不能证明所有论文都能无人值守地完成 |
| 算法与实验实现 | 已产生多种真实算法、数据处理、基线及实验入口；部分运行会发现问题后修正重跑 | 一些改写改变了算法语义，另一些实验缩小了规模或缺少对照 |
| 论文主张验证 | RSA、SCAFFOLD 等已有核心现象的较强支持；其他论文也有局部成功 | 多篇核心优势没有出现；理论证明与完整经验主张不能由局部实验代替 |
| 自动评价 | 已有逐项实现、设置和结果评分，可定位许多缺口 | Judge 会误认对象、引用错误结果或使用错误公式，尚不足以独立承担入库验收 |
| 可复用算法库 | 已积累候选实现与实验材料 | 现有分析尚未给出统一的算法保真、独立运行及跨任务复用验收结果，不能给出可信入库数量 |

**我的阶段判断是：项目已经有了批量复现能力摸底的基础，正在从“能生成并执行复现任务”走向“能判断哪些产物值得信任”。** 建设可复用算法库所需的质量判断，目前仍有明显缺口。

### 1.2 目前最值得记住的结论

1. **Codex 能完成相当一部分复杂的复现工作。** 它能阅读论文与官方材料，构建实验，修正一些数学或数据处理错误，并留下真实结果。把它仅看作代码补全工具，会低估这批已经展示的能力。
2. **Codex 还不能被默认视为可靠的论文复现验收者。** 同一运行可以修掉明显错误，却留下目标与梯度不一致、更新路径改变或实验范围不足的问题。
3. **ReasFlow 的部分 Skills 确实被使用了。** 知识卡检索和绘图有真实调用，实验类指令有读取记录；完整多 Agent 流程及各 Skill 的有效性尚未得到证明。
4. **当前 B 没有显示出更高的整体实验结果分。** 但分数受评测错误和实验协议差异影响，不能据此将全部差距归因于 ReasFlow，也不能用这一批否定其所有能力。
5. **下一步的核心是建立可信产物的验收闭环。** 应从现有案例提炼能发现真实错误的检查，再用受控复测检验 Pipeline 和 Skills 是否补上短板。

## 2. 这一批到底测试了什么

### 2.1 实际任务与工作流程

本批任务要求 Agent 交付独立复现仓库，覆盖支撑论文核心贡献的方法、真实 baseline、数据、指标与正式实验。Agent 维护论文主张清单 `CLAIMS.json`，并在 `CLAIM_RESULTS.json` 中把结果映射到源码、配置和正式输出。任务允许随着理解加深修订主张，同时要求诚实记录部分复现、未复现和客观阻塞。[实际任务说明](/Users/zanehuang/work/OptiRepro/reports/cpu30/analysis-2026-09-06/trajectory/1904.12017-A.observable.md:25)

输入包括论文、元信息、允许的数据与官方代码资料。因此，这批测试的是**给定这些材料和任务支持时，Agent 能否完成独立复现交付**。它没有单独证明“只有 PDF、没有官方实现时的能力”，也没有单独测量论文检索、数据获取或上游论文结构化模块的效果。[本批设计中的输入范围](/Users/zanehuang/work/OptiRepro/docs/superpowers/specs/2026-09-01-cpu30-server-ab-reproduction-pipeline-design.md:40)

| 环节 | 谁在做什么 | 这批值得关注的实际行为 |
| --- | --- | --- |
| 下发任务 | Controller 建立 A/B 任务并启动执行 | 共同要求是完整复现与可验证交付 |
| 理解与计划 | Agent 阅读论文、数据和官方材料，组织主张与实验 | 有真实的公式和协议恢复，也有后来才发现的误读 |
| 实现与运行 | Agent 编写、迁移或改写算法，先小检查，再正式实验 | CPU 改写和缩小预算有时改变了目标实验 |
| 诊断与迭代 | Agent 检查输出、修正问题、重新运行 | 两侧都出现科学纠错；纠错并不总是充分 |
| 外部维护 | Monitor / 控制器处理继续、恢复等交互 | 轨迹中的 user 角色可能是维护消息，不能自动当成人类提供了算法答案 |
| 交付与评价 | Agent 整理仓库和证据，Validator 检查交付，独立 Judge 逐项评价 | 结构齐全、Agent 自评与科学主张成立之间仍有差距 |

例如 RSA A 保存了“认可当前方案，请继续执行”和中性继续消息；这些消息解释了执行如何延续，却不能被当作人类教会了 RSA 算法。相应事件见 [RSA A 公开交互](/Users/zanehuang/work/OptiRepro/reports/cpu30/analysis-2026-09-06/trajectory/1811.03761-A.observable.md:215)。另一方面，现有分析也不足以证明所有任务全过程都没有外部维护。这里评价的是实际 Pipeline 下的执行能力。

### 2.2 A/B 的含义

A 是原生 Codex 条件，B 是相同 Codex 执行基础上的 ReasFlow `experiment` 角色与技能配置。已核对的模型配置为 `gpt-5.6-sol`、相同提供方与推理强度；B 仍通过 Codex 的文件和命令工具执行许多操作。用 `exec_command` 读取技能文件或运行技能脚本，本身可以构成 Skill 使用，不能因为工具名称通用就判为“没用 Skill”。[配置证据](/Users/zanehuang/work/OptiRepro/reports/cpu30/analysis-2026-09-06/trajectory/1904.12017-B.config.json)

这是一组完整任务条件的比较。两侧自行决定的种子数、步长、实验规模和实现方式并不总一致；这些决定正是能力分析的一部分，但也意味着单项数值不能脱离协议比较。本批还有启动 CPU 集合重叠的记录，因此不能作严格的系统效率排名。本文主要分析实现、科学结果与决策过程。

## 3. Codex 与 ReasFlow 已经展示了哪些能力

### 3.1 分数给出的总体信号

Midloop 检查算法实现与实验设置；Bigloop 检查实验结果。下表按论文等权，避免一个条目特别多的论文主导整体印象。

| 已完成的 16 对论文 | A：Codex | B：ReasFlow 配置 | 能支持的解读 |
| --- | ---: | ---: | --- |
| Midloop 平均分 | 74.22% | 75.13% | B 的实现和设置综合分略高 |
| Bigloop 平均分 | 46.16% | 40.73% | B 的实验结果分较低 |
| Midloop 达到门槛 | 7/16 | 8/16 | B 多一篇达到这一层门槛 |
| 两层同时达到门槛 | 2/16 | 2/16 | 两侧都是 RSA 与 stochastic-gradient SCAFFOLD |

Bigloop 中 B 相对 A 为 4 篇更高、10 篇更低、2 篇相同。以上是原 Judge 对该完成子集的结果，**不是“代码有多少百分比正确”或“算法库有多少百分比可以放心使用”**。完整 CPU30 的最终情况尚不能由这 16 对推算。[配对分数来源](/Users/zanehuang/work/OptiRepro/reports/cpu30/analysis-2026-09-06/score_analysis.json)

### 3.2 按能力看，进展比一个总分更具体

| 能力 | 已有正面证据 | 仍暴露的边界 | 对算法库建设的含义 |
| --- | --- | --- | --- |
| 从论文恢复方法 | ADMM、RSA、PPS、ProxRR 等有具体更新与算子实现 | DREAM、IRLS、ManPQN 存在核心求解或尺度问题 | 同一 Agent 可以实现一篇的主体，也可能误实现另一篇关键环节 |
| 组织真实实验 | 有真实数据、多 baseline、多配置和重复实验 | BEER 模型缩小、IRLS 网格缩减、Chicago 提前停止 | 文件齐全不能代替目标实验覆盖 |
| 主动发现并修正错误 | RSA 修数据尺度与攻击语义；SCAFFOLD 修采样后重跑 | 正式结果形成后仍有残留偏差 | 自查有价值，但需要独立的算法和实验检查 |
| 解释负结果 | DREAM、ManPQN 等保留未复现结果与限制 | 发现排序不对后，未必能定位并解决根因 | 诚实负结果可以入资料库，但不能被检索成已验证的方法性能 |
| 使用增强工具 | B 成功读取知识卡、调用绘图脚本 | 缺少工具使用导致结果改善的因果证据 | Skill 应按解决了什么问题评价 |
| 形成可复用资产 | 多个工作区已有模块、配置和可运行入口 | 未统一验证干净环境重跑、接口替换与新任务迁移 | “完成一次复现”和“成为可复用算法组件”需要分别验收 |

这些判断的逐篇依据见后文。特别是，“B 的某些实验覆盖更广”与“B 的最终结果分更低”可以同时成立：额外覆盖可能没有得到目标关系，也可能存在关键实现偏差或评测误判。

### 3.3 现在还不知道什么

目前不能确定 Codex 在全部目标论文上的稳定成功率，不能确定移除官方代码后成功率如何变化，也不能确定同一论文重复运行是否稳定。本次分析未通过系统化的模块替换或新任务实验验证跨论文复用能力。ReasFlow 各 Skill 的独立贡献同样没有通过消融实验确定。

这不是说已有产物没有价值，而是明确下一阶段该测量什么。对于项目目的而言，“能把有效实现从这批产物中稳定识别出来”，是紧接着要解决的问题。
