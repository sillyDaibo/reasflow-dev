## 8. Judge 怎样帮助判断，哪里需要独立复核

### 8.1 分数的基本含义

一项检查通过就得到该项全部权重，失败得到零分；该层分数等于通过权重之和除以总权重。Midloop 门槛为 80%，Bigloop 为 85%。Judge 的 confidence 不参与加权。正文中的“通过条目数”和评分表中的“权重得分”因此可能不同。

例如 RSA A 的 Bigloop 通过权重为 35，总权重为 36，得到 97.22%；它并不表示论文 97.22% 的科学内容已经被独立证实。ManPQN 的结果层有 361 个检查项，而 ProxRR / FedRR 只有 3 个，单项粒度也差异很大。

### 8.2 与算法库质量最相关的评测问题

| 问题 | 已发现的具体例子 | 如果直接用分数入库，会发生什么 |
| --- | --- | --- |
| 量规写错算法 | 分布式 VI 的 p/γ 写反；SCAFFOLD 的控制变量符号错误 | 正确实现可能被拒绝，甚至诱导后续修成错误公式 |
| 对象或实验错配 | BEER 用 MLP 结果支持 CNN；LocalSGD 用 δ 扫描支持 λ 主张 | 后续使用者误以为目标模型或目标机制已被验证 |
| 引用其他结果 | 分层模型 B 引用了旧运行；IRLS B 的判词引用 A 路径 | 当前实现获得了不属于自己的证据 |
| 参考值被当成实测 | 去模糊某项使用论文表值，忽略真实重复实验均值 | 看似数值复现成功，实际没有相应测量 |
| 属性含义不对 | IRLS 用真值生成器的 support_size 支持恢复结果稀疏性 | 输入被正确生成，却被误当成算法成功恢复 |
| 比较口径过窄或不固定 | 分层模型结果更优却超出双向容差；SCAFFOLD 饱和被要求完全无改善 | 有意义的局部复现被低估，跨论文分数解释失真 |

每一项均在对应论文章节提供具体来源。不能把这些错误作为忽略所有低分的理由：DREAM 的混合递推、IRLS 的加权求解、BEER 的模型与训练偏离都有独立于 Judge 的代码或实验依据。**评价必须同时容纳“实现有问题”和“判定有问题”这两种情况。**

全部逐项量规、权重、A/B 原始判词通过各篇末尾的评分明细链接查阅。它们保留为证据参考；本文不把原判词全部复制进正文，也不把未独立复核的判词称为已证实事实。

## 9. 接下来应该做什么

### 9.1 先建立对现有产物的清楚判断

第一步就是完成本报告所做的梳理：明确 Pipeline 阶段、每篇实际结果、关键偏离、技能使用和代码复用限制。这一步的产物应成为现有任务的能力基线，而不是随着后续重跑不断覆盖的“最新最好结果”。

接下来建议为每个候选库建立简短的研究使用说明：算法名称及具体变体、适用假设、已核对的核心更新、覆盖的实验、支持的主张、已知偏离、使用入口。不能用一个“completed”标记承载全部含义。本文逐篇给出的用途判断可以作为这份说明的起点，但还需要真正执行入库验收。

### 9.2 用四个有代表性的案例，验证验收流程能否发现真正的问题

以下是建议的下一轮小规模工作，尚未执行。选择四篇是为了覆盖不同失败机制，不是为了挑选容易得到高分的样本。

| 案例 | 为什么先选它 | 下一步应具体验证什么 | 做完后能回答什么 |
| --- | --- | --- | --- |
| 2503.07594：SCAFFOLD | 核心经验现象较强，适合作为正向参照 | 更新符号与采样语义、正文和官方代码轮数冲突、统一口径的重复结果、独立入口重跑 | 较成熟产物能否形成可信、可复用的最小范例 |
| 1904.12017：分层模型 | 算法与部分应用结果较好，但原结果分偏低 | ADMM 算子对应、基线语义、Chicago 收敛范围，以及清除旧运行证据后的评价 | 验收能否识别“有用实现但评分不可靠” |
| 2212.02387：DREAM | 已有核心方法偏差的直接证据 | 目标与梯度的一致性、FastMix 参考递推，再运行受影响的同协议实验 | 验收能否挡住“文件齐全但数学机制错误” |
| 2306.04961：IRLS | 同时暴露核心子求解与实验覆盖缺口 | 权重算子、加权约束子问题的数值正确性、预先固定的相变实验范围 | 验收能否区分实现不足、运行不足和真正负结果 |

验收成功的标准应是：正确实现获得恰当支持，已知错误被准确定位，未运行内容被标为缺失，负结果被如实保留。不能把所有曲线都调到优于 baseline 当作验收成功。

### 9.3 把案例中发现的缺口转成 Pipeline 的具体约束

**在实现环节增加与论文机制对应的检查。** 梯度法检查目标与梯度是否一致；混合递推与小型参考实现逐步对照；约束方法检查可行性与子问题求解；随机重排检查样本访问和每步更新语义。检查项目应随算法类型变化，不能仅检查文件、变量名或测试是否返回绿色。

**在实验环节维护独立的论文覆盖清单。** Agent 的计划允许修订，但原论文所需的主实验范围要保留。缩减数据、种子、模型或网格时，交付中要清楚显示偏离及未验证主张，避免最终计划变小后掩盖遗漏。清单从论文及允许材料提取，不向执行 Agent 泄露隐藏评分答案。

**在评价环节先验证证据身份和含义。** 每项判断必须对应当前运行、当前方法、当前数据与目标指标；明确区分论文参考值、实际测量和 Agent 自述。遇到理论等价写法、随机波动或协议冲突，应给出可解释判定，不能只匹配名称或要求字面数值相同。

**在复用环节做真实使用检查。** 除了复跑论文实验，还应选一个小型独立任务调用其核心算法或替换 baseline，检查接口、依赖、停止条件和配置能否清楚使用。这是对“能为后续研究提供算法库”的直接检验，当前批次尚未系统完成。

### 9.4 再测 ReasFlow 是否补上了这些缺口

先明确每项增强要解决什么。例如实验设计 Skill 的目标可以是减少关键 baseline 遗漏，实验执行 Skill 可以是保持正式结果与协议一致，产物检查 Skill 可以是发现尺度或算子错误。

然后在相同任务与资源条件下，对照开启和关闭该增强的结果，必要时重复运行。记录有意义的决策链：读取了哪条指令或知识，随后改变了什么实现或实验，最终是否解决了对应缺口。这样才能区分“Skill 被使用”“Skill 执行成功”和“Skill 提高复现质量”。

当前证据支持继续以 Codex 为执行基础进行验证，也支持有针对性地试验 ReasFlow 的增强；尚不足以据此确定最终系统选型。优先把错误发现与可信验收做实，再把有效机制推广到其余任务，并继续完成尚未纳入分析的论文。

## 10. 用什么判断项目正在接近目标

建议后续进展围绕四个问题汇报：有多少任务形成了可检查交付；有多少论文核心主张得到可信支持；有多少算法实现经过独立复用验收；哪些失败能够被系统正确识别和解释。这些数量应分别统计，不能相互替代，也不应先填一个未经验证的成功率。

对本批而言，可以确认已经有 16 对完整交付与评分样本，若干论文有明确局部成功，也有可以定位的真实失败。统一可信入库数量、重复稳定性和跨任务复用能力仍待实测。

**项目下一阶段最有价值的进展，是能稳定地告诉研究者：这份代码实现了什么，哪些结果可以依赖，哪些地方还需要修正，并且这些判断能够被独立验证。**
